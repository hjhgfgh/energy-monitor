> 阶段目标：补齐技术栈中「前端可视化」与「容器化」两块拼图，并拿到网关层的量化压测数据。

## 3. 网关压测数据（量化结论）

压测对象：`GET /api/devices/latest-data`（Sentinel 限流 QPS=5），时长 15 秒。

| 指标 | 20 并发 | 2 并发 |
|---|---|---|
| 总请求 | 168,073 | 66,712 |
| **网关总吞吐** | **11,204 QPS** | 4,447 QPS |
| HTTP 200 | 75（≈5/s，精确等于阈值） | 75（≈5/s） |
| HTTP 429 | 167,998 | 66,637 |
| 其他错误 | 0 | 0 |
| **P50 / P95 / P99** | **0.7 / 4.1 / 22 ms** | **0.4 / 0.7 / 0.9 ms** |

**叙述口径**：网关在 20 并发下保持 1.1 万+ QPS 的处理能力且零错误；Sentinel 限流精确放行 5 QPS，超额请求毫秒级 429 快速失败（P99 22ms），**不消耗后端数据库资源** —— 这就是「在网关层限流」的价值证明。

## 4. 发现并修复的缺陷

1. **P3 拆分引入的静默回归（重要）**：`em-device-access` 的新 application.yml 丢了
   `energy.processor.mode: kafka`，而 `LoggingDeviceDataProcessor` 是 `matchIfMissing=true`，
   导致接入层「只打日志不投递」的兜底实现悄悄生效——模拟器上报正常、服务无报错、
   但 Kafka 零消息、数据库零新增。**发现线索是数据库 last_t 停在旧时间戳。**
   教训：`matchIfMissing=true` 的条件装配在重构迁移时是隐性地雷；用户无感知的数据断流
   要靠「数据新鲜度监控」而不是「服务是否报错」来发现。
2. **前端推送格式与实际不符**：大屏代码最初按想象写 `type:'DATA'` + 顶层字段，
   实际 RealtimeMessage 是 `{type:'data', data:{...}}`（小写、嵌套、epoch 毫秒时间戳）。
   用 WsTest 抓到真实帧后才对齐——**不要对消息格式做想象，先抓真实样本**。
3. PowerShell scriptblock 不能在 .NET `Task.Run` 里安全执行，压测改用 Add-Type 内嵌 C#。

## 5. 关键实现说明（设计要点）

- **WS 鉴权**：浏览器 WebSocket 握手无法自定义 header，网关 JWT 过滤器扩展支持
  `?token=` 查询参数（仅 WS 场景），HTTP 请求仍走 `Authorization` 头。
- **业务服务端口不对容器外暴露**：compose 只映射网关 8090 与设备 TCP 9000——
  JWT 透传头（X-User-*）只在网关之后可信，这是不暴露内部端口的原因。
- **大屏数据流**：初值走 REST（最新数据 + 历史回填 + 告警分页），增量走 WS 推送；
  曲线固定保留 120 个点避免内存无界增长。

## 6. 使用说明

```bash
# 前端开发
cd em-frontend && npm install && npm run dev      # dev 模式自动代理到网关 8090

# 前端构建并集成到网关
npm run build   # 产物已同步到 em-gateway/resources/static，重新打包网关即可

# Docker（需先启动 Docker Desktop）
docker compose up -d        # 一键起全部；首次构建镜像时 compose 会按 build 段自动构建

# 网关压测
powershell -File scripts/gw-bench.ps1 -Threads 20 -Seconds 15
```
