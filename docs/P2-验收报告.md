## 二、架构变化

```
P1：  Netty ──► DeviceDataProcessor(直连入库) ──► MySQL

P2：  Netty ──► Kafka Producer ──► device-data (3 分区)
                                      │
                                      ├─► [em-data-persist 消费组] 批量落库 + 更新缓存 + WebSocket 推送
                                      └─► [em-alarm 消费组]        规则判定 + 分布式锁去重 + 写告警
```

两个消费组消费**同一份数据**，各自独立推进 offset —— 这正是 Kafka 带来的解耦：
新增「告警计算」需求时，接入层和落库逻辑一行没改。

## 四、压测数据

### 4.1 吞吐

模拟器：5 台虚拟设备 × 50ms 上报间隔（设计 100 条/秒）

| 指标 | 实测 |
|---|---|
| 落库总行数 | **8514** |
| 设备数 | 5（每台 1700~1705 条） |
| 时间跨度 | 85 秒 |
| 实际吞吐 | **8514 / 85 ≈ 100 条/秒**（与设计一致） |
| Kafka 消费延迟 | 两个消费组 × 3 分区，**LAG 全部为 0** |

生产端 100 条/秒持续 85 秒，消费端零积压，说明当前配置下消费能力有余量。

### 4.2 告警

| 指标 | 实测 |
|---|---|
| 告警记录 | 3 条（设备 1001 / 1002 / 1004 电压超过 240V 阈值） |
| 每设备告警数 | **各 1 条**（去重锁生效，无重复告警） |
| 去重锁 | Redis 中 `alarm:dedup:{deviceId}:{ruleId}`，TTL 5 分钟 |

同一设备在 85 秒内出现多次超过阈值的电压（实测最高 254.35V），
但只产生 1 条告警记录 —— 这验证了分布式锁确实在起作用。

### 4.3 索引优化对比（同一 SQL，仅索引有无之差）

```sql
SELECT id, device_id, voltage, electric_current, power, collect_time
FROM device_data
WHERE device_id = 1001 AND collect_time >= '2026-09-16 07:08:39'
ORDER BY collect_time DESC LIMIT 100;
```

| 指标 | 有 `uk_device_time` | 无索引 | 差异 |
|---|---|---|---|
| type | **range** | **ALL**（全表扫描） | — |
| 扫描行数 | 1705 | 8020 | **4.7 倍** |
| filtered | 100% | 3.33% | — |
| Extra | 无 filesort | **Using filesort** | 多一次排序 |

建索引语句：

```sql
ALTER TABLE device_data ADD UNIQUE KEY uk_device_time (device_id, collect_time);
```

**为什么这样建**：`device_id` 选择性高放最左；`collect_time` 既参与范围查询，
又与 `ORDER BY` 顺序一致，从而**同时消除 filesort**。
用唯一索引而非普通索引，是因为它还要承担消费幂等的职责。

## 五、本阶段发现并修复的缺陷

### 5.1 `collect_time` 秒精度导致数据被静默去重（严重）

**现象**：消费端已处理 352 条，数据库只有 114 条。

**根因**：`collect_time` 声明为 `DATETIME`（秒精度），而设备 300ms 上报一次，
同一秒内的多条数据在唯一索引 `(device_id, collect_time)` 看来是**同一条**，
被 `ON DUPLICATE KEY UPDATE` 覆盖掉了。

**修复**：改为 `DATETIME(3)`（毫秒精度）。修复后落库 251 条 vs 消费 252 条，基本 1:1。

**教训**：引入唯一索引做幂等时，必须回头检查索引列的实际精度是否足以区分数据，
否则幂等机制会变成静默的数据丢失。

### 5.2 float → BigDecimal 的精度失真

**现象**：告警内容显示「电压为 240.72999572753906」。

**根因**：`BigDecimal.valueOf(float)` 会先隐式转成 double，带入二进制浮点误差。

**修复**：统一经 `Float.toString` 中转。修复后显示「247.93」。

### 5.3 清库后 Redis 去重锁仍在有效期内

**现象**：重建数据库后新的异常电压不再产生告警。

**原因**：这不是缺陷而是设计使然 —— 去重锁 TTL 为 5 分钟，
而数据库被重建后告警记录消失，锁却还在。

**运维注意**：清空告警表时需同步清理 Redis 的 `alarm:dedup:*`。

## 六、已知限制

- **消费失败会无限重投**：某条消息若因数据本身有问题而永远处理失败，会阻塞该分区。
  生产环境需引入重试上限 + 死信队列（DLQ）。
- **WebSocket 单实例**：session 存在本进程内存，多实例部署时只能推给连到本实例的客户端。
  跨实例推送需借助 Redis Pub/Sub 或 Kafka 转发。
- **分布式锁的 Redis 单点风险**：主从切换瞬间存在锁失效窗口。
  对「避免重复告警」这一场景可接受；要求绝对互斥需 Redlock。
- **`device.status` 在线状态未随连接变化更新**，P3 接入 Spring Security 时一并处理。
- **设备侧尚未鉴权**（`device.secret_key` 字段已建但未启用校验）。
